## A. 競品分析

### A.1 既有內部調研檢驗（引擎選型輪 + 10 平台 UI/UX 對標）

既有競品分析有兩輪、兩份文件：(1) 引擎選型輪 —— `dev_docs/research_open_source_backtest_platforms.md`（2026-05-31 產出，已於 commit 54ce175 從 repo 刪除，本次自 git 歷史 `54ce175^` 完整恢復），地毯式盤點 30+ 開源回測框架/工具，場景為「台股 100 檔 × 10 年 portfolio、FinMind+TWSE 資料、M4 接 Shioaji、性能目標 <30 分鐘」。報告本身的最終建議是選項 C（vectorbt 核心 + 借鑑 TQuant-Lab 台股微結構、捨棄 rqalpha、自寫 PBO/DSR/WFA），但文首 follow-up 補註（2026-05-31）載明實際採納的是擴充版「TQuant-Lab 主骨架 + vectorbt 副引擎 + 自寫 PBO/DSR」，正式決策落在 ADR-005（TQuant-Lab zipline fork 主骨架，Supersedes ADR-001 rqalpha 路線）、ADR-006（資料源改 FinLab 付費版，非報告假設的 FinMind）、ADR-007（雙引擎 zipline+vectorbt）、ADR-008（三模式共用 strategy code）、ADR-009（雙儀表板+Telegram 告警）與 17_m2_to_m5_master_plan.md。(2) UI/UX 對標輪 —— `dev_docs/web_design/03_uiux_benchmark_and_reinforcement_plan.md`（2026-06-02，deep-research 多 agent，10 平台 + 10 維度差距 + 7 張流程圖），核心結論：當前設計 100% 投資在大廠最不投資的「監控」階段，研究迭代迴圈（Ideate→Author→Configure→Backtest→Analyze→Compare→Validate→Promote→Monitor 九階段）UX 完全缺席；10 維度中 7 個 CRITICAL（IA/authoring/run 提交/run 追蹤/多 run 比較/防過擬合工作流/晉升 gate）+ 3 個 HIGH（A–D 面板時機錯置、空狀態死胡同、設計系統不適配研究互動）。差異化機會：無任何大廠同時做到「試驗次數→DSR deflate + OOS sealed vault + PBO/DSR 紅線自動擋晉升」。脈絡錨點：M2 IS gate FAIL → 回 M0 重設進場（ADR-017），是兩份結論的共同痛點驗證。新一輪分析須檢驗的時效假設：所有 stars/版本數據止於 2026-05；vectorbt 開源版凍結於 v1.0.0（新功能進 PRO $20/月）；TQuant-Lab 綁 TEJ 但專案後改用 FinLab 付費資料（報告的 TEJ 綁定劣勢評估已部分失效）；A–D 面板「時機錯置」判定依賴「尚無 edge、無 paper/live 部署」的前提，若已近上線該優先序應上調（文件自承）。

**可直接轉化為設計決策的要點**：

- 選型已成定局且經兩層演化：報告建議「vectorbt 核心 + 借鑑 TQuant-Lab」→ 實際採納「TQuant-Lab(zipline fork) 主骨架 + vectorbt 副引擎 + 自寫 PBO/DSR」（ADR-005/006/007/008/009）。新一輪競品分析不應重開引擎選型，除非發現 (a) TQuant-Lab/zipline-reloaded 停止維護、(b) vectorbt 開源凍結產生實際阻礙、(c) 台股原生新框架出現（如 polars_backtest_extension 成熟）。
- 報告的三個排除底線可直接沿用免重查：授權陷阱（pypbo/backtesting.py AGPL、vectorbt Commons Clause、polars_backtest_extension PolyForm NC、mlfinlab 商業化）、棄維護（backtrader/zipline/pyfolio 原版、catalyst）、市場不符（vnpy/freqtrade/jesse/hummingbot/hikyuu 無台股）。
- 台股生態的結構性 gap 仍是本專案定位：「完全免費 + 完整台股日曆/微結構 + 接 Shioaji」的開源框架不存在——backtest_platform 就是在填這個洞。
- 核心設計決策：把「一次回測」升格為一等公民 Run 物件（config+資料快照+code/engine 版本+metrics+status+lineage），runs 主表為 single source of truth——目前 run_id 是散落 4 張時序表的孤兒鍵，此為後端最大空白、M0 最高優先。
- 防過擬合必須從展示升級為強制：M2 IS gate FAIL 已實證「唯讀指標+人工紀律」無約束力。落地三件套（全可純 Python/CLI TDD）：IS→WFA→OOS 不可逆狀態機 gate_state.py、OOS sealed vault（未過 gate 前 CLI/UI 皆不可讀、存取計次留痕）、試驗次數→DSR 自動 deflate（QC/MLflow 都沒做的差異化亮點）+ PBO>0.5 / DSR<1.0 紅線自動擋晉升。
- 晉升做成不可逆狀態機 Draft→Backtested→Validated→Paper→Live→Retired，FAIL 回流 Draft（ADR-017「IS gate FAIL 回 M0」的系統化）；單人版以「限提交+鎖 OOS+強制 paper 觀察期（如 60 交易日）」替代 Numerai 真錢後果；假設預先註冊為 run 必填欄位，OOS 後自動比對事前承諾。
- IA 唯一關鍵重構：sidebar 從「strategy selector + A–E 監控平鋪」改兩段式（上段 Research：策略庫/New Run/Runs/Compare/Sweep/Validate/Promote，下段 Monitor：A–D 降為 /monitor/* live 子視圖）；Panel E 從監控唯讀重定位為 Validate gate。已落地為 13 份 page 規格（pages/research_01~08 + system 2 + home/fleet/trade_review 3 補頁）。

### A.2 開源回測 / 量化平台（2025-2026 現況）

針對 10 個開源回測/量化平台（2025-2026 現況）的橫向研究。核心觀察：(1) 業界正在形成「向量化快速探索 → 事件驅動高保真驗證」的雙引擎工作流共識（vectorbt.pro → nautilus/LEAN），這正好對應本專案 zipline-reloaded + vectorbt 的雙引擎設計，方向與主流一致。(2) 三模式一致性（backtest/paper/live）最成熟的參考是 freqtrade（同一 IStrategy 介面、僅持久層 in-memory vs DB 不同）與 nautilus（同一確定性 event loop、部署零改碼）與 LEAN（config.json 的 environments 切換 IDataFeed/ITransactionHandler/IRealtimeHandler）。(3) 防過擬合工具化：freqtrade 的 lookahead-analysis 與 recursive-analysis 是可直接抄的自動偵測機制；學術級 CPCV/PBO/DSR 主流平台幾乎都沒內建，MLFinLab 已閉源收費，free 生態靠 purgedcv、ml4t-diagnostic 等小庫——本專案的真偽閘（PBO/DSR/WFA/survivorship-clean）反而是罕見的差異化強項。(4) 研究工作流最完整的是 qlib（宣告式 task + RD-Agent LLM 自動因子挖掘）與 zipline Pipeline API（因子/動態選股）。(5) 台股（TWSE）在所有主流平台都是一等公民缺口，全部需自建資料層，這是本專案 standalone 的必然選擇。

**可直接轉化為設計決策的要點**：

- 雙引擎方向已被 2026 業界共識背書：『向量化快速探索（vectorbt/vectorbt.pro）→ event-driven 高保真驗證（nautilus/LEAN 級）』正是本專案 vectorbt + zipline-reloaded 的分工。維持此分工，別讓向量化引擎承擔撮合/風控細節，也別用 event 引擎做第一階段海量掃參。
- 三模式共用策略碼的邊界設計，抄 freqtrade 的『唯一差異在持久層』原則：backtest 用 in-memory、paper/live 用 DB-backed，同一策略介面注入不同的 DataFeed/ExecutionHandler（LEAN 的 config environments 是組態化範例，nautilus 的確定性 event loop 是零改碼範例）。三者交叉印證同一設計哲學。
- 直接把 freqtrade 的 lookahead-analysis 與 recursive-analysis 概念工具化，做成本專案研究工作流的自動 gate：連鏈回測 + 戳策略比對指標/進出場位移偵測前視偏誤；不同資料長度算指標比對尾列變異偵測遞迴/startup-candle 洩漏。這兩個是『人工 code review 難察覺』的洩漏，值得 CI 級自動化。
- 訊號強制 shift 1 根 K 棒 + OHLC 一致性驗證（low≤open/close≤high）作為資料契約(doc 21)的基本防線——freqtrade 內建、成本低、擋掉最常見的未來函數。
- 本專案的真偽閘（PBO/DSR/WFA/survivorship-clean）是罕見的差異化強項：主流平台幾乎都只停在『walk-forward + 過擬合警告』，學術級 CPCV/PBO/DSR 沒有內建，free 生態僅剩 purgedcv、ml4t-diagnostic 等小庫（MLFinLab 已閉源收費、timeseriescv 自 2018 停更且有正確性問題）。建議：CPCV 優先於單純 WFA（研究證實 CPCV 有更低 PBO、更高 DSR），並自建/採用 ml4t-diagnostic 的 correlation-adjusted K_eff DSR 而非簡化版。
- qlib 直接印證本專案的核心痛點：官方明說缺歷史成分股會殘留 survivorship bias——本專案已做 survivorship-clean 撞到 ~0.9 Sharpe 牆，這證明那道牆是『真實 alpha 稀缺』而非工具問題，別回頭懷疑清洗步驟。多數平台其實偷懶跳過這步，本專案的嚴謹是對的。
- 研究工作流藍本抄 qlib：宣告式 task 組態驅動整條 data→train→backtest→analysis pipeline + Point-in-Time 資料庫（歷史時點取當時版本，避免財報修訂洩漏）。台股財報修訂/point-in-time 因子務必用 PIT 設計。RD-Agent 的 LLM 自動因子挖掘可作為『掃描下一個候選 edge』的方法論。
- 台股在地化規則層抄 rqalpha 的 mod 架構：其 A 股 T+1/漲跌停/交易日曆處理與台股（漲跌停 10%、T+2、當沖）高度同構，取其可替換 data source/broker 的擴充模式，不綁其平台。
- corporate actions 正確性是股票回測底線：zipline-reloaded 原生處理 split/dividend，務必確認 fork 對台股除權息調整的支援，否則自建；backtesting.py 等輕量庫缺此能力，不可作核心。
- 平台治理分層抄 Hummingbot：交易引擎 / 管理 API(FastAPI) / 告警遠控(Discord) 解耦成獨立層，對應本專案 fleet lite 營運；策略以組態快速衍生（config-driven 模板）降低新策略上線成本。
- 上游維護風險管理：zipline-reloaded（近月無 PR、社群 fork）與 vectorbt 開源版（維護模式、能量轉 pro）與 vectorbt.pro（單一作者 bus factor）都有可持續性風險。本專案應保留關鍵邏輯的自行 patch/替換能力，勿把不可替換的核心綁死單一上游。

### A.3 大型金融機構內部系統設計原則

機構級量化系統（GS SecDB/Slang、JPM Athena、BofA Quartz、BlackRock Aladdin、Two Sigma、Citadel、Jane Street、Bloomberg PORT/AIM、Man AHL Arctic/ArcticDB）的公開資訊歸納出 10 條核心設計原則，可分為「值得縮小規模照抄」與「機構規模才需要（對個人過度設計）」兩類。

【核心設計原則】(1) 單一真相源 — SecDB/Aladdin/Quartz 把 trades/positions/product data/market data 統一在單一 bi-temporal 框架，全公司單一版本真相、杜絕重複造輪。(2) 依賴圖/計算圖 (Dependency Graph) — SecDB 的「特殊能力」，reactive DAG 把定價與風險做成節點，參數變動沿圖傳播、按需重算、快取+失效；Athena/Quartz/Pioneer 都是此範式複製，別家花 $bn 級資源仍難完全重現。(3) 部位/風險一致性 — Aladdin 提供跨內外部資產單一即時風險視圖。(4) 研究到生產 pipeline — Two Sigma「raw+curated 雙層資料」讓研究者立即上手、data-as-code + CI/CD、「ice cube」可重用資料契約滿足 90% 用例；quant 與 dev 共用同一碼庫。(5) 時點/bi-temporal 資料 — 對抗 survivorship（研究顯示 S&P500 survivorship bias 使回測年化虛增 1.5–2.0%）與 lookahead bias；Bloomberg 專門推 PIT 產品；此為機構共識剛需。(6) 風控前置 — pre-trade risk check（微秒級）、kill switch、position limits，FINRA 15c3-5 市場接入規則強制。(7) 共用碼庫/不重複造輪 — SecDB 內部「開源」、Athena 50M 行共用、Jane Street 全棧單一 OCaml。(8) 擁抱領域複雜度但用動態型別 — Athena 拒絕硬塞 relational model，Python duck typing 處理異質商品、熱點降到 C++。(9) 不可變 + 版本化 — ArcticDB immutable version + time travel + snapshot（類 git）。(10) type safety 換可靠性 — Jane Street 用 OCaml 型別系統換小團隊高生產力與系統可靠。

【對個人台股 standalone 平台的判斷】必須縮小照抄：時點/bi-temporal 資料（本專案 survivorship-clean 已做對，0.9 Sharpe 牆正是誠實面對的結果）、單一真相源的 position/risk state 層、風控前置（pre-trade + kill switch）、共用碼庫（三模式共用策略碼）、不可變版本化研究產出。過度設計（機構規模/監管/多人才需要）：自建語言（Slang/OCaml）、1M cores 雲端、自建 reactive 計算圖引擎、cross-asset 全域即時風險聚合、bi-temporal 全資產統一框架、企業級 OMS/EMS。最直接可用工具：Man AHL ArcticDB（Python-native + 版本化 + time travel + PIT + serverless 免 DevOps），值得評估作為研究時點資料層補充/取代 TimescaleDB。

主要來源：efinancialcareers SecDB/Slang 系列、Athena Conf42/TechRepublic（35M 行 Python 2 無法及時升級）、BofA Quartz careers、BlackRock Aladdin/Wikipedia、Two Sigma platform-thinking、Google Cloud Citadel（1M cores）、Jane Street technology、Bloomberg PORT/AIM 產品頁與 PIT 產品發布、MongoDB/GitHub man-group/ArcticDB。

**可直接轉化為設計決策的要點**：

- 時點/bi-temporal 資料層是機構唯一『必須縮小規模照抄、不可省』的原則。本專案 survivorship-clean 已做對方向 — 0.9 Sharpe 牆正是誠實面對 survivorship/lookahead 後的真實結果（機構研究：survivorship bias 使回測年化虛增 1.5–2.0%，很多假 edge 就藏在這 2% 裡）。掃描下一個 edge 時務必維持 PIT 紀律。
- 強烈建議評估 Man AHL ArcticDB 作為研究資料層（補充/部分取代 TimescaleDB）：Python/pandas 原生、immutable 版本 + time travel + snapshot 天然提供 PIT 與『重現任一次 backtest 資料狀態』，serverless 免 DevOps 契合 single-user standalone。TimescaleDB 保留給 live/paper 的即時時序寫入，研究層改用 ArcticDB 的版本化快照。
- 建立『單一真相源』的 position/risk state 層：backtest/paper/live 三模式不只共用策略碼，還應共用同一 position/risk ledger 抽象，避免各引擎（zipline vs vectorbt）各算一套部位/風險造成 drift。這是把本專案既有『三模式共用策略碼』延伸到狀態層。
- 風控前置（pre-trade check + kill switch + position limit）縮小照抄到 live 模式：機構視此為不可省的第一道防線（FINRA 15c3-5、微秒級檢查）。本專案已有兩段式驗證閘 + Heat/熔斷，符合 risk-first；補上 live 下單前的 pre-trade position limit 與一鍵 kill switch（Discord 可觸發）即完整。
- 採用 Two Sigma『raw + curated 雙層資料 + data-as-code + ice cube 資料契約滿足 90% 用例』：把 FinLab/FinMind 原始資料（raw）與 survivorship-clean/PIT 對齊後的 curated 層明確分離，研究者用 raw 立即開工、curated 供正式回測。本專案 Bundle/Pydantic schema 已是契約雛形，強化 raw/curated 分層即可。
- 不可變 + 版本化研究產出對抗 overfitting：借鏡 SecDB bi-temporal / ArcticDB snapshot，每次 backtest/研究 run 快照化、可 time travel 重現，並把 experiment log 當 lab notebook。配合機構紀律『限制單一 idea 的 backtest 次數、theory-first 縮小搜尋空間』— 下一個 edge 應 theory-driven 假設驅動，而非參數暴掃（避免重蹈 0.9 Sharpe 牆）。
- 明確避免的機構級過度設計（機構規模/監管/多人協作才需要，個人不做）：自建 DSL/語言（Slang/OCaml）、自建 reactive 依賴圖計算引擎、1M cores 雲端 orchestration、cross-asset 全域即時風險聚合、bi-temporal 全資產統一框架、企業級 OMS/EMS。個人站在成熟 Python 生態（zipline/vectorbt/pandas/ArcticDB/FastAPI/React）上即可。
- 堅持單一技術棧一致性（借鏡 Jane Street 無 silo + type safety 精神）：全流程 Python + Pydantic 型別/schema 驗證貫穿研究/回測/paper/live，避免多語言碎裂；用 schema 驗證換取『機構級 type safety』的可靠性，尤其在資料契約與策略參數邊界。
- 保持模組邊界可獨立（借鏡 Bloomberg AIM 模組化 + Aladdin 反面教訓）：資料/回測/風控/告警/儀表板高內聚低耦合、可獨立測試替換；同時避免把所有風控壓進單一黑箱模型（Aladdin 系統性風險教訓），保留人工可解釋的風控規則層。
- 『擁抱領域複雜度』要與個人平台 YAGNI 平衡：Athena 拒絕硬塞 relational model 是對的，但那是 cross-asset 全球場景。台股單一市場、單人，不需 cross-asset 抽象與過度泛化的商品模型 — schema 保持簡單、按需擴充，別預先為不存在的資產類別建抽象。Athena 的 Python 2→3 遷移失敗警訊：從一開始鎖定現代 Python 並保持依賴可升級。

### A.4 個人 / 散戶量化商業產品與 SaaS

2025-2026 面向個人/散戶量化交易者的產品可分四類：(1) 雲端全棧研究+實盤（QuantConnect / LEAN 開源）；(2) 圖表+腳本回測+告警觸發（TradingView / Pine Script，本身非執行引擎，需 webhook+VPS 補全）；(3) no-code/AI 自動化+內建券商（Composer.trade、TrendSpider）；(4) 開發者優先券商 API（Alpaca、台灣的永豐 Shioaji / 富果 Fugle / 富邦）。台灣本土則為 FinLab（研究導向、資料品質+內扣成本+lookahead 偵測為賣點）、XQ 全球贏家（看盤+回測+下單一體、XScript）、MultiCharts 券商版（期貨當沖自動下單，NT$667-900/月）、TQuant Lab（TEJ 機構級資料）。四大痛點的解法成熟度差異極大：資料成本/品質與部署維運（VPS、監控）市場供給充足；但「驗證信心」（>90% 策略上線失效、PBO/DSR/WFA、survivorship/lookahead clean）幾乎沒有零售 SaaS 認真做——這正是多數平台的空白，也是本專案兩段式驗證閘的差異化定位。定價帶：純研究/圖表 US$13-50/月或 NT$700-800/月（FinLab）；no-code 自動化 US$24-137/月；認真跑多策略雲端實盤 US$200-300/月；台灣券商 API 多為免費（靠下單佣金）。自建 vs SaaS 分界線：當「軟體開發+資料授權+基礎設施維運」總成本超過平台訂閱，且不需要平台無法提供的東西（機構級台股資料、嚴謹驗證閘、三模式共用碼、完全客製風控）時，買現成划算；反之自建才有意義。本專案作為 single-user standalone，其存在理由必須落在 SaaS 買不到的三處：FinLab 級台股資料 clean + 嚴謹真偽閘 + backtest/paper/live 三模式共用策略碼。

**可直接轉化為設計決策的要點**：

- 定位象限明確：本專案屬『自建/build』象限（Python 雙引擎+Shioaji），競爭對手不是 FinLab/XQ 這類 SaaS，而是『使用者自己用 backtrader+券商 API 拼裝』。價值主張必須是『把散戶自建會踩的坑（資料 clean、驗證閘、監控告警、三模式一致性）預先工程化』，否則不如叫使用者直接用 FinLab。
- 驗證信心是最大市場空白，也是唯一穩固護城河：>90% 策略上線失效，但沒有一個零售 SaaS 把 PBO/DSR/WFA/survivorship-clean 做成強制 gate（FinLab 只做 lookahead 偵測+成本內扣，TradingView/Composer/TrendSpider 幾乎不做）。本專案兩段式驗證閘（真偽閘+配置閘）應作為對外定位的第一賣點，而非內部工程細節。動能/資金流雙 NO-GO 撞 0.9 Sharpe 牆的誠實，正是這個賣點的可信度背書。
- 資料成本/品質痛點的解法是『內扣成本 + clean 資料』而非『更多資料』：FinLab 的核心賣點與本專案方向一致（單次成本 0.585%、月換手年侵蝕約 7%，未內扣成本的免費工具反而誤導）。本專案應把『成本內扣 + survivorship/lookahead clean』做成預設不可關閉行為，並在報表明示，對標 FinLab 的可信度定位。
- 部署維運需雙層監控，不能只做 uptime：市場證據顯示『server 100% 在線但下單程式已凍結數小時』是散戶最大隱性虧損來源。本專案 Discord 告警必須同時覆蓋 (1) 服務可達性 uptime + (2) 交易執行層（process 存活、券商延遲、成交確認），而非只推每筆下單通知。這是相對 TradingView webhook 拼裝方案的具體差異化。
- 定價/成本錨點供 PM 參考：純研究工具 US$13-50/月（TradingView）或 NT$700-800/月（FinLab）；no-code 自動化 US$24-137/月（Composer/TrendSpider）；認真跑多策略雲端實盤 US$200-300/月（QuantConnect）；券商 API 幾乎免費（Alpaca/Shioaji/Fugle，靠佣金）。本專案 single-user standalone 的『隱含價值』= 省下的 SaaS 訂閱 + 自建時間成本，PM 論述應用 QuantConnect 的 Build-vs-Buy 框架（軟體+資料+基礎設施 vs 訂閱）量化。
- 三模式共用策略碼（backtest/paper/live）是差異化亮點但非市場既有訴求：多數平台把回測與實盤視為兩套（TradingView 需 webhook 橋接、FinLab 下單是後加、MultiCharts 需下單機雙設定）。本專案『同一份策略碼三模式一致』直接消除『回測賺、實盤賠』的實作漂移風險，應明確納入產品敘事——這是 QuantConnect/LEAN 少數也強調的一致性價值。
- UX 借鏡但守住驗證底線：Composer 的『自然語言→60 秒生成策略』與 XQ/FinLab 的『看盤-回測-下單一體不斷鏈』是散戶期待的體驗基準；本專案 FastAPI+React 可參考。但必須用驗證閘擋在生成與部署之間，避免複製 Composer『快速生成助長過度擬合』的反模式。
- 開放 Python 生態 vs 封閉專有語言是結構性優勢：XQ(XScript)、MultiCharts(EasyLanguage) 皆封閉，無法接 ML/現代資料科學。本專案 zipline/vectorbt + Python 可接 scikit-learn/因子研究，這在『掃描下一個候選 edge』的研究工作流（DOE/truth gate/paper replay）上是實質優勢，應作為對進階散戶的訴求點。

## B. 五視角審查全文

### B.1 產品經理（PM）視角

從產品經理視角看，這個專案的「實質產品」與「文件宣稱的產品」已經分裂成兩個東西。PRD（dev_docs/02，v3.0，2026-06-01）仍將產品定義為「四層共振戰法回測平台」，商業目標、US-001~006、成功指標全數綁定一個已被 ADR-023 判定為「負 edge、毀價值、應砍」的策略；決策沿革表止於 D-018（2026-06-04），ADR-023~029 這七個真正定義現今產品形態的決策（策略廢止、兩段閘、策略契約/registry/dispatch、研究工作流標準化）全部缺席。而實質產品——16 WBS banner 與程式碼所呈現的——是一台「個人量化研究作業系統」：策略是可拋棄的假設，平台的價值是用 PBO/DSR/WFA/survivorship-clean 的審判庭誠實地殺掉壞策略、讓極少數真 edge 走 paper→live 晉升管線。這個 pivot（ADR-018 研究迴圈優先 + ADR-025 兩段閘）在方向上是正確且罕見地誠實的——連續四個策略結構 NO-GO 沒有引發放水，反而 triangulate 出「台股大中型 long-only ~0.9 Sharpe 結構牆」的可操作結論，這本身就是平台價值的最強證據。但 PRD 從未被重寫來承載這個價值主張：依現行 PRD 的成功判準，專案已經失敗；依實際運作，平台是唯一被證實的資產。這個敘事真空是目前最大的產品風險。

更嚴重的是，pivot 後的產品主軸「審判庭即產品」正被審判庭自身的實作缺陷架空。標準化研究工作流（ADR-029）的 truth_gate 把年化 Sharpe 與日報酬變異數餵進 per-period DSR 公式（實測年化 Sharpe 0.333 → DSR=1.000000），DSR>0.95 這道核心通縮檢查退化成符號檢查；宣稱的 OOS holdout（cfg.is_end）從未被評估；survivorship_clean=True 寫死；ADR-025 第二段 SizingGate 零呼叫者。inst_flow 的「TRUTH GATE REAL」判決來自已刪除的 7 支一次性 scripts，如今用標準化工作流重跑會得到不可信的數字——產品唯一的 paper-ready 候選，其判決在現行程式路徑上不可重現。對一個把「不自欺」寫進 ADR 的產品而言，這是價值主張級的缺陷，不只是工程 bug。

功能範圍上，❌ 排除清單品質很高（不做多市場/期權/多帳戶/leaderboard/staking，展現清醒的單人邊界意識），但執行層出現「機構級過度設計 vs 個人剛需缺口」的錯配：67 端點 REST API（大面積 typed-stub）、17 頁 React SPA 三 zone + Cmd-K、InfluxDB+Grafana+Discord 三層監控先建完，違反 ADR-018 自己立下的「補齊研究迴圈前不擴張監控」鐵律；同時個人使用者的真剛需——after-close 排程器（收 live OOS 的唯一 blocker）、資料資產備份/DR（8.E/8.F）、parquet 快取不丟歷史、紙上交易組合層風控真的生效、以及最基本的「前端能提交一個 run」（NewRunPage 對現行後端必然 422）——全部未交付或壞損。單一使用者的每日研究主迴圈（提交→看報告→比較）在 UI 端目前是斷的。

Persona 方面，「單人開發者本人、研究者/運維者雙帽」在 02/05 有隱含描述但從未正式化，standalone 自託管的安全/部署假設（無 auth 是否可接受、單機路徑慣例）也從未在 PRD 明文，導致 doc 25 要求 Bearer、後端零實作、前端硬編碼 dev-token 的三方矛盾。

重新定位建議：PRD v4.0 應把產品正名為「個人量化 edge 驗證工廠 + 晉升管線」，平台 KPI（判決正確性、每個策略假設的驗證成本/週期、血統可重現性）與策略 KPI（兩段閘判準）分列；策略降為 consumable。優先序上，Must 是修好審判庭與研究血統（DSR/OOS/survivorship、runs DDL、per-strategy gate）並用修正後的閘重現 inst_flow 判決、修復前端主迴圈、重寫 PRD；Should 是用最簡 cron 實作 after-close 排程開始收 live OOS、備份、paper 風控接真持倉、文件債分級凍結；Could 是最小 CI 與圖表；Won't（維持 gated）是艦隊營運層、Shioaji、Monitor stub 補齊與全面 auth。一句話總評：方向對、紀律真、敘事與判決引擎的可信度必須立刻補課，否則「平台優先」只是一個沒有文件與證據支撐的口號。

#### 發現

### B.2 首席架構師視角

本審查以首席架構師視角，對 backtest_platform（約 15.7k 行、140 個 .py）做 smells → principles → fixes 三段式架構審查，聚焦六個問題面。總體判斷：這是一個「判決層（validation/risk/monitoring）品質優異、契約層（ADR-027 strategies/protocol）縫畫對了、但舊縫殘骸未清、三模式一致性與資料血統保證尚未成立」的系統。

(1) 模組邊界：核心壞味道是 engines↔strategies↔research 三角依賴。engines/protocol.py:28-36 同時 import 四層策略的具體 StrategyConfig 與 research.is_harness 的五個底線私有 helper，違反其自身「engine-agnostic」docstring；反向地，三隻策略的 research_config.py 只為拿 DEFAULT_UNIVERSE 常數就 import engines.zipline_adapter.bundles.finmind_bundle，連帶觸發模組頂層 import zipline 與 register("finmind") 全域副作用（finmind_bundle.py:314）。這同時違反 dev_docs/09 明訂的 DIP/ADP/SDP 三原則。api 層本身乾淨（薄轉接 + envelope），問題在它轉接的 research 層。

(2) ADR-027 的縫位置正確——把契約放在「輸出」（StrategyRun：returns/trades/gate-ready metrics）而非輸入，registry 用純 dict，符合單人專案的 KISS。但接縫沒畫完：判決標準（gate）不在契約內，run_and_judge 一律用四層專屬 DEFAULT_GATE（is_harness.py:130/176），使 momentum/inst_flow 經 API 的 run 永遠 INCOMPLETE；RunConfig.engine 被驗證、寫入 run_id hash 與 ledger 但 _run_is_core 完全不 dispatch（血統造假）；truth_gate 用 hasattr 猜 config 欄位重造滑價壓力，無視契約已有的 with_extra_slippage/slippage_sharpe；engines/protocol.py 整個是被 ADR-027 實質取代的 Lava Flow。

(6) 可擴展性：下一個 10 隻策略先斷在「gate 不隨策略 dispatch」（全部 INCOMPLETE）與 runners.py import 副作用註冊；10 年資料先斷在 parquet 覆寫毀史、JSONL 全檔掃描 O(N)、DOE 掃描逐 config 重複載入 panel 無共享快取。修復優先序：P0 = paper 風控真實倉位、runs DDL 對齊、parquet 增量合併、DSR 單位統一；P1 = 拆三角依賴、gate 入契約、engine 欄位去留。

### B.3 軟體設計模式視角

本審查深讀 backtest_platform/src/backtest_platform/ 實際程式碼，從設計模式視角評估。整體圖像是「兩個世界並存」：純函式核心（risk/、validation/、orchestration/daily_flow.py、strategies/protocol.py）的 pattern 運用達到教科書水準，而接縫層（engines/、orchestration/collaborators.py、api/ overrides、data 外部呼叫）的 pattern 要麼是假的、要麼缺席。

### B.4 QA / 測試策略視角

整體判斷：92.9%（實測 93.15%）的覆蓋率**不是 smoke test 灌水，但也不是它看起來的品質保證**。實測 1,058 個後端測試、約 1,959 個 assert（平均 ~1.9 assert/test），抽查 tests/data/test_adjustment.py（21 個除權息測試，含現金+股票股利複合、壞資料 skip 路徑）、tests/data/test_universe_builder.py（point-in-time 下市納入/排除）、tests/validation/test_wfa.py（明確的 no-leakage 不變量：IS 全程先於 OOS、purge/embargo 邊界）等，斷言密度與行為針對性在 data/validation/risk 這些純函式模組是**紮實的**。真正的問題是覆蓋率是「行覆蓋」而非「判決覆蓋」：research/workflows 的測試 shape-only（只驗型別與 0-1 範圍），導致 truth_gate 把年化 Sharpe＋日報酬變異數餵進 per-period DSR 公式這種**判決級 CRITICAL bug**（DSR 檢查退化為符號檢查、n_trials 通縮失效）在全綠測試下存活——而同 codebase 的 validation/full_report.py 就有正確實作可當 oracle，測試卻沒拿來對拍。金字塔形狀與 dev_docs/22_test_strategy.md 宣稱的 70/20/10 完全脫節：實際 99.1% unit / 0.9% integration（9 個）/ 0% E2E，是柱狀不是金字塔；doc 22 宣稱的 recon 矩陣 R-001~R-007、hypothesis、pytest-benchmark、golden baseline、tests/{unit,integration,recon,e2e} 目錄、六個 markers **全部不存在**，文件凍結在 2026-05-31。量化平台特有缺口呈兩極：除權息與下市的 point-in-time 測試品質好；但停牌與漲跌停無任何測試（taiwan_stock_rules.py 明文承認 ±10% TradingControl 未實作、limit-up 樂觀成交）、hypothesis property-based 零使用（grep 零命中）、無 checked-in golden master（regression_vs_m1 與 vectorbt 對拍共 7 個 integration 測試依賴本地 parquet cache，fresh checkout 即 skip，且對拍 harness 本身被 pyproject omit 出 coverage）、look-ahead 防護僅止於 WFA fold 邊界不變量，無 signal 層 leak detector。前端更嚴重：44 個 vitest 全是淺層 smoke，且 mock 的 API 形狀就是錯的那套（strategy_id/status/頂層 sharpe vs 後端真實的 strategy/gate_status/巢狀 metrics），**測試綠燈直接掩蓋了 NewRunPage 對現行後端必然 422 的 CRITICAL drift**；@vitest/coverage-v8 未安裝使 80% 規範無法量測；唯一 Playwright spec 是端點連通性審計（不判斷、只記錄），非使用者旅程。CI 品質閘門：.github/workflows/ 不存在，所有 gate（coverage 80%、integration、OpenAPI diff）純靠本地自覺，doc 22 §8 與 ADR-021/025 的 CI 承諾從未落地。結論：這是一個「單元層強、契約層與判決層盲、自動化強制力為零」的測試體系——最高 ROI 的補強不是再堆單元測試，而是 (1) 判決級 oracle 測試、(2) 前後端契約測試、(3) 最小 CI、(4) checked-in golden master。

#### 發現

- **[CRITICAL] 覆蓋率 93% 是行覆蓋非判決覆蓋：shape-only 工作流測試放過 truth_gate DSR 單位錯誤（CRITICAL bug 全綠存活）**：tests/research/workflows/test_truth_gate.py 僅 assert isinstance/0-1 範圍/verdict∈三值，不驗 DSR 數值合理性、OOS 視窗是否被讀取、survivorship 前提。結果 research/workflows/truth_gate.py:50-62 把年化 Sharpe（validation/metrics.py:182 ×√252）＋日報酬變異數餵進 per-period DSR 公式（實測年化 Sharpe 0.333 → DSR=1.000000，正確單位應為 0.503 REJECTED）、run_truth_gate 從未使用 cfg.is_end（宣稱的 OOS holdout 零評估）、survivorship_clean=True 寫死——三個判決級缺陷全部在 1053 pass / 93.15% coverage 下存活。同 codebase 的 validation/full_report.py:37-40 有正確 DSR 實作（per-period + 強制 cross-trial variance），可直接當測試 oracle 卻未被用於對拍。這證明覆蓋率數字對本專案最關鍵的資產（閘門判決正確性）沒有保護力。
- **[CRITICAL] 前端測試 mock 形狀與後端真實回應互斥，綠燈掩蓋 NewRunPage 必然 422 與 RunsTable/RunReport 滿版「—」**：frontend/src/features/research/pages/RunsTablePage.test.tsx:32 mock {strategy_id, status:'done', sharpe 頂層}，但後端 /runs 真實回 {strategy, gate_status:'PASS', metrics 巢狀}（api/routers/runs.py:38-51）；NewRunPage.test.tsx 只驗 hypothesis 欄，放過送 preset 欄對 extra=forbid 後端必 422（schemas.py:17-28）。型別生成源 frontend/openapi.json stale（仍含已刪的 /presets）。測試套件與 e2e/audit/endpoint-audit.spec.ts（忠實記錄真後端）是互相矛盾的兩套事實——手寫 mock 無契約校驗，是整個前端測試體系的結構性失效。
- **[CRITICAL] CI 品質閘門完全不存在：.github/workflows/ 目錄不存在，所有 gate 靠本地自覺**：實測 ls .github/workflows → No such file or directory。dev_docs/22_test_strategy.md §8 的 GitHub Actions YAML、ADR-021/ADR-025 §9 的 OpenAPI CI diff、doc 25 §9 契約治理全是紙上草案。後端 80% coverage gate（pyproject.toml:115）、前端 vitest、Playwright audit、schema 防漂移測試（tests/data/test_init_sql_schema.py）沒有任何機器強制執行點。ADR-028 的 runs 表 DDL drift（init.sql preset vs db_writer strategy，寫 DB 必炸）與 openapi.json stale 兩起事故都是「無 CI 強制」的直接後果。
- **[HIGH] 測試金字塔實為 99.1/0.9/0 柱狀，與 doc 22 宣稱 70/20/10 完全不符；E2E 為零**：pytest 收集 1058 個測試，integration marker 僅 9 個（tests/engines/zipline_adapter/validation/ 7 個 + tests/data/test_db_writer.py 2 個，後者預設 skip 需 POSTGRES_INTEGRATION=1），pytest e2e 為 0。dev_docs/22_test_strategy.md:15-34 宣稱 Unit 70%/Integration 20%/E2E 10%；§1.3 的 unit/e2e/recon/live markers 在 pyproject.toml:117-120 不存在（--strict-markers 下 `pytest -m recon` 直接報錯）。三模式（backtest/paper/live）E2E smoke、使用者旅程（create run→report→gate→promote）全缺。唯一 Playwright spec（frontend/e2e/audit/endpoint-audit.spec.ts:206）唯一斷言是 results.length === routes.length，對 4xx/5xx 不 fail，是審計工具非測試。
- **[HIGH] 雙引擎對拍測試存在但脆弱：僅 7 個、依賴本地 parquet cache（fresh checkout 即 skip）、harness 被 omit 出 coverage、門檻三處三個數字**：tests/engines/zipline_adapter/validation/test_cross_check_vectorbt.py 與 test_regression_vs_m1.py 內容品質不錯（match_pct>=0.999、相對 1%/絕對 10bps 兩段式容差、trade count 對齊），但：(1) 全部依賴 `zipline ingest -b finmind` 產生的本地 data/parquet cache，無 cache 即 skip——本機恰好有 cache 所以這次跑過，任何 CI/新環境都會靜默跳過；(2) 對拍 harness 原始碼（src/.../zipline_adapter/validation/*）被 pyproject.toml:139 omit 出 coverage，93% 數字不含它；(3) 驗收門檻在 02 PRD（<0.1%）、17 master plan（<0.5%）、16 WBS 5.B.3（相對 1%/絕對 10bps）三處互相矛盾，測試實作採第三種但無文件收斂；(4) doc 22 §4 的 R-001~R-007 對拍矩陣無任何自動化對應。另 RunConfig.engine='zipline' 被接受但 _run_is_core 永遠跑 sim，代表研究路徑實際上根本沒有第二引擎可對拍。
- **[HIGH] 無 checked-in golden master 數值回歸基準：策略 metrics 無凍結快照，重構後的數值漂移無人守門**：grep golden 僅命中 doc；tests/ 無 regression 目錄、無任何「已知輸入 → 凍結的期望 metrics」fixture。regression_vs_m1 用的是「兩個活實作互相對拍」而非 checked-in baseline——若兩邊同時被改壞（或共用同一有 bug 的 signals 函式），測試照過。inst_flow 這種已判 TRUTH GATE REAL、即將 paper 的策略，其 Sharpe/DSR/PBO 數值沒有任何 snapshot 測試保護；validation/ 的 dsr.py（78%）、pbo、wfa 也沒有對 López de Prado 論文已知數值範例的 oracle 測試。量化平台最怕的「重構後數字悄悄變了」目前完全裸奔。
- **[HIGH] 前端覆蓋率工具壞損＋hooks/api client/services 零測試**：`npx vitest run --coverage` 立即失敗（MISSING DEPENDENCY @vitest/coverage-v8，package.json devDependencies 無此套件），.claude/rules/testing.md 的 80% 規範對前端無法量測。66 個非測試 src 檔僅 22 個有測試，全集中在 pages 淺層 smoke（mock fetch → render → 單一文字斷言）；所有 hooks（useEndpoint、useMonitor、11 個 research hooks）、所有 api client（features/*/api/*.ts，即 drift 重災區）、services/{http 之外的 ws,queryClient}、router.tsx、AppShell、5 個共用 components 零測試，無任何表單提交/mutation/錯誤路徑互動測試。
- **[MEDIUM] property-based testing（hypothesis）完全缺席，validation/risk 純函式模組是最該用卻沒用的地方**：grep 'from hypothesis' 全 repo 零命中，doc 22 宣稱的 hypothesis 測試未落地。validation/（dsr/pbo/wfa/metrics/gate_machine）與 risk/（12 條 EX 規則、circuit_breaker）是狀態全注入的純函式模組——正是 property-based 測試 ROI 最高的標的（例：任意報酬序列下 0≤DSR≤1、WFA fold 永不重疊、RiskGate 對排列不變、adjustment factor 單調性）。現有 test_wfa.py 的不變量測試其實已經是 property 風格，只差用 hypothesis 把 example 空間放大。truth_gate 的單位錯誤若有「DSR 對 n_trials 單調遞減」這條 property 就會被抓到。
- **[MEDIUM] 時間序列邊界覆蓋兩極：除權息/下市測試紮實，停牌/漲跌停零測試（引擎明知樂觀成交）**：好的一面：tests/data/test_adjustment.py 21 個測試涵蓋現金+股票股利複合、壞 ratio skip、亂序資料；tests/data/test_universe_builder.py:115 與 test_finlab_source.py:74 有 point-in-time 下市納入/排除測試（anti-survivorship）。缺口：(1) 停牌/暫停交易無任何測試與實作；(2) 漲跌停——engines/zipline_adapter/controls/taiwan_stock_rules.py:94-98 明文承認 ±10% TradingControl 未實作、limit-up 日 fill_at_open 系統性樂觀，此已知偏差沒有對應的 xfail/回歸測試釘住；(3) look-ahead 防護僅 WFA fold 層邊界不變量（test_wfa.py:168-），無 signal 層 leak detector（如「把未來資料 shift 進 loader，訊號不得改變」的反事實測試）；(4) survivorship_clean=True 在 truth_gate.py:73 寫死且無測試挑戰。
- **[MEDIUM] per-path coverage gate 未配置，關鍵模組低於文件宣稱門檻**：doc 22 §7.1 要求 strategies/ 95%、validation/ 90% 獨立 gate，實際 pyproject 僅全域 80%。實測：strategies/conformance.py 74%（契約守門者自己覆蓋最低）、validation/tearsheet.py 77%、validation/dsr.py 78%（DSR 正是出 CRITICAL bug 的區域）、research/cli.py 57%、jobs/job_store.py 64%。另 doc 22 §7.2 引用 --cov-fail-under=65 與實際 pyproject.toml:115 的 80 矛盾，同檔 §1.2 目錄制與 §2.1.1 路徑兩種體系並存。
- **[MEDIUM] dev_docs/22_test_strategy.md 整體凍結在 2026-05-31，宣稱的測試資產七成不存在**：tests/{unit,integration,recon,e2e,performance,regression,fixtures} 七個目錄、unit/e2e/recon/live markers、R-001~R-007 對拍矩陣、pytest-benchmark（100 檔×10 年<30min）、freezegun、golden baseline、tests/spike/ 全部無實作對應；Streamlit 測試對象（dashboard/streamlit_app.py）已被 ADR-015 廢止但 §3.3/§5 仍在寫。slow marker 定義語義兩處差 60 倍（doc: >5min vs pyproject: >5s）且零使用。違反專案 code-doc-sync 鐵律，且讓「文件宣稱的策略」與「實際金字塔」的比對失去意義——22 號文件目前描述的是一個不存在的測試體系。

#### 建議（優先級/工作量）

- **[P0/M] 為閘門判決建立 oracle 級測試並修復 truth_gate DSR（測試先行釘住正確行為）**：以 validation/full_report.py 的正確 DSR 實作為 oracle，對 research/workflows/truth_gate.py 寫判決級測試：(1) 固定合成報酬 + n_trials 掃描，斷言 DSR 對 n_trials 單調遞減、與 full_report 路徑數值一致（tolerance 內）；(2) 斷言 cfg.is_end 界定的 OOS holdout 確實被讀取（可用 loader spy）；(3) 已知應 REJECTED 的案例（年化 Sharpe 0.333/n_trials=24）必須 REJECTED。這組測試會先 RED（抓住現有 CRITICAL bug），再修 truth_gate。這是全專案最高 ROI 的測試投資——保護的是『要不要投錢』的判決。
- **[P0/M] 建立最小 CI pipeline（GitHub Actions）：pytest+coverage gate、vitest、OpenAPI/DDL drift check**：單一 workflow 三個 job：(1) 後端 uv run pytest（含 --cov-fail-under=80，33 秒即可全跑）；(2) 前端 npm test + 安裝 @vitest/coverage-v8 後 --coverage；(3) drift 檢查——app.openapi() 與 frontend/openapi.json diff、init.sql 與 db_writer._RUNS_COLS 欄位對齊斷言（補進 test_init_sql_schema.py）。這一步同時堵住 openapi stale、runs 表 DDL drift、doc 25 registry 漂移三類已發生事故的根因。無 CI 之前，任何測試策略補強都沒有強制力。
- **[P0/M] 前端契約測試：以真後端 OpenAPI 重生型別，mock 改由 schema 生成，補 NewRunPage 提交路徑測試**：(1) 從活後端重新導出 openapi.json 並 npm run gen:api，讓 TypeScript 編譯期直接暴露 strategy_id/status/preset 等欄位錯誤；(2) 單元測試的 mock 資料改為由 openapi schema 生成（如 msw + openapi-backend 或手寫 schema-validated fixtures），禁止手寫任意形狀；(3) 對 NewRunPage 補『填表→送出→斷言 request body 形狀』的 mutation 測試。這把『測試綠燈掩蓋 422』這類事故從結構上消除。
- **[P1/L] 建立 checked-in golden master：合成 bundle + 凍結 metrics 快照，讓對拍與回歸測試脫離本地 cache**：(1) 造一個小型合成 parquet bundle（5-10 檔、2-3 年、含除權息/下市事件）checked in 到 tests/fixtures/；(2) 對每個 registry 策略跑一次，凍結 metrics（sharpe/cagr/mdd/trades）為 golden JSON，加 approx tolerance 回歸測試；(3) cross_check_vectorbt 與 regression_vs_m1 改為可吃合成 bundle，讓 CI 也能跑對拍而非 skip；(4) 順帶把 src/.../zipline_adapter/validation/* 從 coverage omit 移除。同時把雙引擎容差統一為一個數字（建議採現行實作的相對 1%/絕對 10bps）回寫 02/17/16 三份文件。
- **[P1/M] 在 validation/ 與 risk/ 導入 hypothesis property-based 測試**：優先標的：dsr（0≤DSR≤1、對 n_trials 單調、對 sr 單調）、wfa（任意參數下 fold 不重疊/不越界——現有手寫不變量直接升級）、pbo（對 config 排列不變）、metrics（sharpe 對常數平移報酬的行為）、risk_gate（規則對訊號排列不變、heat 上界）、adjustment（factor 單調遞減、raw 欄位保留）。約 15-20 條 property 即可覆蓋最關鍵的數學不變量，且能抓到 truth_gate 這類單位錯誤。加 hypothesis 到 dev dependencies 並在 doc 22 記錄。
- **[P1/L] 補台股特有邊界測試：漲跌停 TradingControl（先 xfail 釘住已知偏差）、停牌、signal 層 look-ahead detector**：(1) 對 taiwan_stock_rules.py 的 ±10% 漲跌停缺口先寫 xfail 測試釘住『limit-up 日不應成交』的期望行為，實作 TradingControl 後轉綠——避免已知偏差被遺忘；(2) 合成 bundle 加入停牌日（volume=0/價格缺漏），測 ETL、signals、broker 三層行為；(3) 寫反事實 leak detector：對 loader 注入 shift(-1) 的未來資料，斷言當日訊號改變（證明訊號讀了未來）或不變（證明無 leak）——對 inst_flow 這種法人資金流策略尤其重要（法人買賣超 T 日盤後才公布）。
- **[P2/M] 重寫 dev_docs/22_test_strategy.md 對齊現況，並配置 per-path coverage gate**：刪除不存在的目錄制/markers/R-矩陣描述，改為記錄實際 domain 制佈局、integration/slow 兩個 markers、實測金字塔與補強路線圖（引用本審查的 P0-P2 項）；統一 slow 語義與 fail-under 數字。同時在 CI 加 per-path 覆蓋檢查（coverage json + 腳本斷言 validation/ ≥90%、strategies/ ≥95%），把 conformance.py 74%、dsr.py 78% 拉上門檻——這兩個檔案分別是策略契約與統計判決的守門者，不該是覆蓋最低的。
- **[P2/L] 補 1-2 條使用者旅程 E2E（Playwright webServer 自動起服務）**：playwright.config.ts 加 webServer（uvicorn + vite preview）使其可進 CI；先補兩條最關鍵旅程：(1) New Run 表單提交 → runs table 出現 → report 頁 KPI 渲染（會立即抓到現有 preset 422 與欄位 drift）；(2) monitor 區 pending_m4 stub 的四態渲染。POSTGRES_INTEGRATION 測試在 CI 用 services: timescaledb 容器啟用，讓 runs 表 DDL drift 這類必炸缺陷有機器暴露點。
- **[P3/M] 性能基準測試（pytest-benchmark）與 JSONL 儲存退化守門**：等 P0/P1 完成後再做：對 is_harness 單次 run、grid sweep、runs_store/job_store 讀寫加 benchmark baseline，slow marker 實際啟用並在 nightly CI 跑。單人研究規模下優先級最低，但 paper daemon 三個月長跑（M4）前應就位。

### B.5 UI/UX 使用者旅程視角

從 UX 研究員視角重建這位單人量化交易者（開發者本人）的端到端旅程後，核心結論是：**IA 骨架已忠實落實 ADR-018／web_design/03 的「研究迴圈優先」藍圖，但旅程的實質承載完全反轉——研究區（旅程核心）在 GUI 內無法完成任何一個完整循環，監控區（旅程末站）反而是接線最好的區域。**

重建的旅程與介面承載如下：(1) **資料 ingest**：CLI（zipline_adapter/cli.py ingest + FinLab/FinMind ETL）為主，GUI /system/data 的 ingest 觸發器（POST /system/ingest async + 輪詢）是全前端少數可完整操作的互動，但 bundle manifest pending，使用者無法在 GUI 確認自己有什麼資料。(2) **策略研究（DOE/IS/sweep）**：實質 100% 由 research/cli.py 12 個子命令（run-is/sweep/doe/compare/go-gates…）承載；GUI 的 NewRunPage 因送已廢棄的 `preset` 欄對現行後端必然 422（NewRunPage.tsx:38-45 vs api/schemas.py extra=forbid），RunsTablePage/RunReportPage 因欄位 drift 滿版「—」，ComparePage 永不渲染——GUI 研究區是「看起來存在、實際不可用」。(3) **驗證晉升（gate）**：CLI validate/truth-gate/promote-check 承載；GUI ValidateGatePage 只顯示 GET /gate/spec 靜態規格 + 4 條 PendingNote，而 useGateState/useValidateWfa hooks 已寫好卻沒接；RunReportPage「送驗證」鈕因 status 欄 drift 永久 disabled——旅程在此死路。(4) **paper**：runtime/paper_daemon 純程式層，GUI 零入口，after-close 排程器是已知 blocker。(5) **live 監控**：GUI /monitor 5 頁與 db_reader 欄位對齊良好，是唯一「CLI→GUI 交接成功」的旅程段，但無圖表（recharts 裝了零使用，PerformancePage 用 30 列文字表代替 equity 曲線）、無輪詢。(6) **退化處置**：doc 03 §4.6 設計的 triage→Cmd-K→回研究區迴路，Cmd-K 與 FirstRunEmptyState 確實已建（doc 03 CRITICAL #9 有落實），但判讀「暫時波動 vs 結構性退化」所需的 live_start_date 邊界圖表不存在，fleet_action 端點是 stub。

**認知負荷爆炸點**有三：第一，「CLI 執行、GUI 檢視」的分工因檢視層欄位 drift 而失敗，使用者跑完 CLI 後打開 GUI 看到空欄，只能退回 CLI `runs`/`compare`，GUI 產生負價值（多一個要對帳的錯誤來源）；第二，契約存在三份互斥真相（doc 25 §6、frontend/openapi.json、活後端 67 條路由），單人開發者要在腦中維護三方 diff；第三，唯一 paper-ready 候選 inst_flow 走 API 時被四層專屬 DEFAULT_GATE 判 INCOMPLETE，GUI 上旗艦策略看起來是壞的。

**最深的設計反諷**：doc 03 §2.3 的核心論點是「唯讀展示 ≠ 工作流強制、儀表盤要接煞車」，但目前前端把這個反模式倒過來實作了——Validate（煞車）是唯讀 pending，Promote（油門）卻完整可寫：使用者可在 GUI 無任何 gate 證據下 draft→paper→live 一路 advance。這比原本被批判的 Panel E 更危險。

**14（實為 17）頁對 single-user 是否過多**：是。M4 前有 5+ 頁無真資料可看（monitor 大半 pending_m4、Alerts pending），研究 9 頁中僅 Sweep estimate 與 Promote 真正可操作。旅程驅動的結論不是砍頁，而是「先救主線、再收斂」：一個 openapi.json 重生成 + 欄名對齊的小 commit 就能救回 Runs Table/Run Report/New Run 三頁（旅程每日主線）；接上已寫好的三組 hooks 即點亮 Sweep/Validate；然後把 17 頁收斂為約 9 個活躍頁（Compare+Sweep 合併、Validate+Promote 串成單一 gate 管線、monitor 5→2、system 2→1）。另外 ADR-029 標準化後的研究工作流（doe/go_gates/truth_gate/paper_replay）是現行研究方法的真相源，GUI IA 中完全沒有它的位置——前端還停在 ADR-018 時代的 run-centric 敘事，這是下一輪 IA 演進必須補的洞。

- **[CRITICAL] 研究旅程 GUI 主線第一步即斷裂：New Run 必 422、Run Report「送驗證」永久鎖死，GUI 內無法完成任何一個研究循環**：旅程「構想→提交 run→看報告→送驗證」（web_design/03 §4.1-4.2 的核心情緒曲線）在 GUI 內每一站都斷：frontend/src/features/research/pages/NewRunPage.tsx:38-45 提交 {preset,...}，後端 api/schemas.py RunCreateRequest 已改必填 strategy+params 且 extra=forbid → 必然 422；RunReportPage.tsx:68/:137 讀不存在的 run.status → 「送驗證」disabled 永真；RunsTablePage.tsx:167-177 讀 strategy_id/status/created_at（後端是 strategy/gate_status/無此欄）→ 滿版「—」。首次體驗：HomePage FirstRunEmptyState CTA → New Run → 422 死路——doc 03 §3 #9 批判的 first-run 死胡同只是換了位置重現。使用者所有研究動作實質退回 research/cli.py（run-is/sweep/doe/compare 12 個子命令）。

- **[HIGH] ADR-018「研究迴圈優先」IA 只落實骨架、實質反轉：煞車（Validate）唯讀 pending、油門（Promote）完整可寫**：骨架達標：frontend/src/app/nav.ts 三區 sidebar Research 在前、CommandPalette.tsx（Cmd-K）與 FirstRunEmptyState.tsx 存在、monitor 降為 /monitor/*——doc 03 §5.2 的唯一 IA 重構確實做了。但實質反轉：(a) ValidateGatePage.tsx 只渲染 GET /gate/spec 靜態規格 + 4 條 PendingNote，gate 狀態機/OOS vault/WFA/PBO-DSR 紅線/試驗計數/power gauge 全無呈現——Panel E→Validate gate 重定位（doc 03 §4.7 關鍵變動）只完成命名；(b) PromotePage.tsx:69-84 的 advance mutation 完整可用，且 UI 無任何 gate 前置檢查——使用者可在零驗證證據下 draft→paper→live 一路晉升。這正是 doc 03 §2.3「唯讀展示≠工作流強制」批判的反模式，且更危險（可寫操作無守門）。後端防過擬合 L4/L5 機制（gate_machine 不可逆狀態機、trials_counter_store、two_stage_gate）存在但 GUI 零接線。
- **[HIGH] 已 shipped 的後端能力被前端 PendingNote 錯標「待後端」，hooks 寫好未接——旅程覆蓋度審計失真**：SweepPage.tsx:64-69 對 POST /research/sweep 顯示「待後端」，但後端 research_sweep.py 已實作且前端 api/sweep.ts + hooks/useSweep.ts 已寫好無人引用；ValidateGatePage 未使用已存在的 useGateState/useValidateWfa（後端 /research/validate/{id}/gate-state、/wfa 已上線）；AlertsPage 對已存在的 /system/alerts/channels、/test 顯示 pending；HomePage 的 fleet_strip/system_health 標 M4 pending，但 getHomeFleet/getSystemHealth API 函式已寫。對單人使用者（前後端都是自己）而言，這些過期陳述會引導他去做已完成的工作。修復成本極低（接線 + 刪 note），是 ROI 最高的旅程修復之一。
